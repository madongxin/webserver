# 客户端「机器人不移动」数据原因分析（2026-11-13）

依据：基线 `client-20261113-221629`、Enforce 复测 `client-20261113-231200`、stall `aoi-stall-20261113-223440.jsonl`，以及对应服务端 A→B 抓取。  
「不移动」在画面上通常有两层含义，数据上要分开看。

---

## 0. 一句话

**不是 GameLogic 没让人走，而是出口贴死 2.6 Mbps 后：自己的 MoveRsp 经常晚于/丢于 2s 超时，别人的 AOI 坐标更是几十秒收不到 —— 客户端表现为自己停步、周围机器人冻住。**

---

## 1. 先拆现象（数据定义）

| 观感 | 数据含义 | 本次是否成立 |
|------|----------|--------------|
| 别人冻住 | 观察者长时间无新 AOI 坐标（`no_aoi` / `sample_age` 大） | **成立（stall 实测）** |
| 自己不走 | 本连接 `move_timeout` 高 / `actual_success_hz` 远低于目标 | **成立（905 bot 分布）** |
| 服务器没算移动 | `move_requests ok` 接近 0 或大量 reject | **不成立** |
| 只开了 enforce 才坏 | 仅 enforce 轮出现 | **不成立**（基线同样贴顶+高超时） |

---

## 2. 原因链（按因果顺序，全部带数）

### 原因 A — 出口已打满（根因容量）

稳态 A→B（压测仍在线）：

| 轮次 | HTB 1:10 吞吐 | 相对 ceil 2600Kbit |
|------|---------------|---------------------|
| 基线 | **2.601 Mbps** | 贴顶 |
| Enforce 复测 | **2.613 Mbps** | 贴顶 |

同期两 Gateway 仅 AOI `move` 帧估算 on-wire：

| 轮次 | gw0 move wire | gw1 move wire | 合计约 |
|------|---------------|---------------|--------|
| 基线 | 1.48 Mbps | 1.44 Mbps | **~2.92 Mbps 量级需求**（还未加 move_reply/enter/leave） |
| Enforce2 | 1.49 Mbps | 1.47 Mbps | 同上量级 |

同时 A 点仍有 backlog（基线 262KB/1180p，Enforce2 176KB/821p），说明 **qdisc 侧持续积压**，不是空闲链路。

→ 下行（AOI + MoveRsp 等）在共享 2.6 Mbps 帽下互相挤占；客户端必然出现「晚到 / 长时间无更新」。

---

### 原因 B — 别人看起来不移动：AOI 坐标断供（主观感）

`aoi-stall-20261113-223440.jsonl`（5283 帧事件，~382s 跨度）：

| 指标 | 数值 |
|------|------|
| 卡顿原因 | `no_aoi` **94.8%**（7232/7629 条 stalled 记录） |
| 阈值定义 | 超过 **3.5s** 无新 AOI 坐标 → `no_aoi` |
| `sample_age` | p50 **46.5s**，p90 **133s**，p99 **168s**，max **171s** |
| `sample_age > 10s` | **82.3%** |
| `sample_age > 60s` | **40.4%** |
| `still_sec` | p50 **42.7s**，p99 **165s** |
| `held_at_sample` / `render_stall` | 仅 4.4% / 0.8%（不是主因） |

对照服务端：同一时期 Gateway 仍在以约 **2500 AOI move 帧/s（两 gw 合计）** 出站。

| 推论 | 依据 |
|------|------|
| 服务器在发别人位置 | AOI move frames/s ≈ 2514（基线）/ 2551（Enforce2） |
| 客户端收不到或极晚 | `no_aoi` 主导 + `sample_age` 数十秒 |
| 画面上「机器人站桩」 | 模型停在最后一次采样点，权威坐标已过期 |

**这是「周围机器人不移动」的直接数据原因：观察端 AOI 更新饥饿，不是逻辑服停止仿真。**

客户端 `aoi_move_events` / `aoi_visible_peak` / visible 列表在两轮导出中均为空 —— 导出未填，记 **无数据**，不能用来否定 stall；stall 文件才是观察端证据。

---

### 原因 C — 自己也经常走不动：MoveRsp 贴 2s 超时

客户端目标 `target_hz=5`，但合计成功频率远低于目标：

| 轮次 | ack 率 | timeout 率 | 单 bot 成功 Hz 均值 | 单 bot 成功 Hz p50 |
|------|--------|------------|---------------------|---------------------|
| 基线 | 82.9% | **16.8%** | 0.64 | 0.82 |
| Enforce2 | 80.7% | **19.0%** | 0.56 | 0.78 |

RPC 延迟（ms）：

| 轮次 | p50 | p95 | p99 |
|------|-----|-----|-----|
| 基线 | 1071 | 1475 | **1884** |
| Enforce2 | 785 | 1588 | **1904** |

Enforce2 按 bot 分布（905 行）：

| 分布 | 数值 |
|------|------|
| timeout 率 p50 / p90 / p99 | 0.19 / **0.86** / **0.98** |
| timeout 率 > 50% 的 bot | **256 / 905（28%）** |
| `move_ack_ok=0` | **18** |
| `actual_success_hz < 0.2` | **190 / 905（21%）** |
| `actual_success_hz == 0` | 18 |

→ 约两成 bot 几乎走不动；近三成半数以上移动请求超时。Sparse 巡逻在超时/busy 时会停步或重发，**自己的角色也会表现为「不移动」或一顿一顿。**

`timeout_before_write=0`：超时发生在 **已写出之后等回包**，不是本地没发出去。

---

### 原因 D — 服务端其实在接受移动（排除「逻辑没跑」）

Enforce2 A→C：

| 实例 | move ok Δ | duplicate_target Δ | dup/(ok+dup) |
|------|-----------|--------------------|--------------|
| logic-0 | 128859 | 38925 | **23.2%** |
| logic-1 | 66301 | 20318 | **23.5%** |

基线客户端 `move_rejected` 仅 **5**（几乎可忽略）。

→ 权威位置在更新；`duplicate_target` 高更符合 **客户端超时后对同一目标重发**（与 resend 15–17% 一致），不是「服务器拒绝移动所以站着」。

MoveRsp 侧服务端仍在发：A→B move_reply 合计约 **770–800 帧/s**，wire 约 **0.43 Mbps/gw**。问题在 **送达时效**，不是「没回包逻辑」。

---

### 原因 E — 不是「开了 enforce 才不移动」

| 现象 | 基线（enforce 关） | Enforce 复测（开） |
|------|-------------------|-------------------|
| 出口贴 ceil | 是 | 是 |
| 客户端 timeout | 16.8% | 19.0%（略差） |
| admitted / defer | 0 / 0 | 0 / 0 |

→ 「不移动」在 **关 enforce 的基线轮已经成立**；开 enforce 没有修好，也没有从数据上单独制造新机制（admitted 未记账）。

---

## 3. 原因优先级（按对「画面冻住」贡献）

1. **出口 2.6 Mbps 打满 + backlog**（容量根因）→ AOI / MoveRsp 排队变晚  
2. **AOI 长时间无新坐标（`no_aoi`，sample_age 可达 1–3 分钟量级）** → **别人冻住**（主观感）  
3. **Move 2s 超时占比 17–19%，尾部 bot 更惨** → **自己停步/巡逻卡住**  
4. **超时触发 resend + duplicate_target ~23%** → 加重上行与逻辑负载，恶性循环（放大项，非第一因）  
5. **EGRESS_ENFORCE 未在指标闭环** → 本应限 AOI 保控制面，实测没起到分流作用（治理失效，不是冻住的直接分子）

---

## 4. 明确不是主因的（数据排除）

| 假设 | 排除依据 |
|------|----------|
| 逻辑服拒绝移动 / 未处理 MOVE | ok 量大；reject≈0 |
| 客户端根本没发移动 | `move_sent` ~29.5 万；`timeout_before_write=0` |
| 纯渲染插值 bug 为主 | stall 里 `render_stall` 仅 0.8% |
| 只是个别 bot | timeout>50% 达 256/905；success_hz<0.2 达 190/905 |
| visible=0 表示地图没人 | 导出字段为空属 **无数据**，且 stall 明确盯到 Bot131 等实体 |

---

## 5. 数据结论（给产品/客户端口径）

- 你看到的「机器人不移动」，数据上主要是：**别人的 AOI 更新断了（数十秒无坐标）**，叠加 **自己的移动回包经常摸到 2 秒超时**。  
- 服务器侧权威仍在跑（大量 `move ok` + 大量 AOI move 出站），但 **2.6 Mbps 共享出口送不完、送不及时**。  
- 要改善观感，数据指向的是 **降 AOI 出站量或提高有效送达（预算真正 defer/分层/外推等）**，而不是先查「逻辑服有没有 Tick」。
